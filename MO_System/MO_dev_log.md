# MO System Development Change Log

This document records the overall development and debugging history for the MO_System project, including version updates, bug fixes, and major functional changes.

## Version history

### v1.8
- Date: 2026-08-08
- Main change: Initialized v1.8 version copies (`MO_system_iTC_v1.8.py` and `MO_system_iTC_v18.ui`) from previous v1.7.
- Details:
  - Duplicated the main executable script and Qt UI layout file to establish the v1.8 baseline.
  - Linked `MO_system_iTC_v1.8.py` to load `MO_system_iTC_v18.ui`.
  - Removed the redundant `get_TDS_peak_pos` logic for `1D_THz` mode. Since the MO system (THz pump, Optical probe) uses Stage2 (PM500) to map out the entire THz waveform over the delay time, the fixed-point peak tracking logic inherited from OPTP is unnecessary and would only waste testing time.
  *(Note: This logic deletion was manually reverted by the user shortly after, in order to preserve the function for potential future OPTP integration testing. The v1.8 file was reverted to its pre-deletion state.)*

### v1.9
- Date: 2026-08-08
- Main change: Patched multiple stability and hardware control bugs inherited from OPTP v1.3-v1.7.
- Details:
  - Fixed MercuryiTC connection exception catching (v1.3 bug): Now safely handles generalized exceptions during connection, calls `.close()`, and properly resets tracking variables (`self.mercuryiTC`, `uid_HTR`, `uid_TEMP`) so subsequent connections don't hang.
  - Fixed QThread lifecycle leak in `iTC_goto_targetT()` (v1.4 bug): Prevents blind overwriting of the temperature stabilization thread by gracefully `.quit()` and `.wait()`ing on any active instance before creating a new one.
  - Resolved instrument shutdown race condition (v1.6 bug): `closeInstruments()` now actively checks for and waits on the temperature stabilization thread to finish before closing the MercuryiTC port, preventing background polling crashes.
  - Patched Stage1 BBD202 (LinearStage) dead-lock vulnerability (v1.7 bug): Changed `connectInstruments()` to use a temporary stage variable during initial homing. If an exception occurs, the temporary handle is safely closed, preventing the COM port from becoming permanently locked.

### v2.0
- Date: 2026-08-08
- Main change: Upgraded polarization calibration file parser to support `.csv` format.
- Details:
  - Rewrote `import_calibration_file()` to safely read standard comma-separated `.csv` files natively using Python's `csv` module.
  - Implemented dynamic handling for empty trailing columns (e.g., missing Stage3_deg) by replacing them with `0.0` to prevent `ValueError` parsing crashes.
  - Preserved fallback logic to read legacy whitespace-separated `.txt` calibration files for backwards compatibility.

### v2.1 (stability fixes back-ported from OPTP)
- Date: 2026-08-10
- Main change: Back-ported the outstanding stability and usability fixes from OPTP v1.9 / v1.91 / v2.3 / v2.4 that had not yet reached this system. Peak-tracking work was deliberately excluded, and the `TPOP_Data` directory name was left unchanged (TPOP is the correct name for this setup).
- Details:
  - **Removed `QApplication.processEvents()` from the high-frequency scan slots** (`update_curr_repeat`, `update_curr_pos`, `update_curr_step`, `update_curr_stepNOs`, `update_lockin_charts`, `update_pol_chart` x2, `update_TDS_FDS_chart`). Those slots already run on the GUI thread via queued connections, so `processEvents()` re-entered the event loop and dispatched the next queued scan signal from inside the current slot. When the scan loop emits faster than the GUI drains - most easily with instruments missing, where there is no hardware latency - the nesting grew without bound until the stack overflowed and the process was killed with no Python traceback. Kept the calls in `connectInstruments()`, `closeInstruments()`, `iTC_goto_targetT()` (button path), `update_temp_hightlight()`, `on_temp_done()` and `set_ControlsEnabledDuringScan()`: those are main-thread user actions or fire only once per temperature point, so they cannot produce unbounded nesting.
  - **Fixed the "Goto T" UI freeze.** `iTC_goto_targetT()` called `self.itc_stab_thread.quit()` followed by an unbounded `wait()`. `quit()` only exits a Qt event loop, and `iTCstabilizeThread.run()` is a plain `while not stop_flag` + `time.sleep()` poll loop with no event loop, so `quit()` did nothing and `wait()` blocked the GUI thread until the old thread happened to stabilize on its own. Now sets the stale thread's own `stop_flag` (not `self.stop_flag`, which would also abort a running scan) and waits with a 2 s timeout. The same dead `quit()` + unbounded `wait()` pair in `closeInstruments()` was replaced with `request_stop()` plus a 10 s bounded wait - that one had been able to hang application shutdown. The 10 s budget is deliberately longer than the 2 s used elsewhere because the worker can take up to one full poll interval to notice the flag.
  - **Hardened the `itc_stab_thread` lifecycle.** It is now initialised to `None` in `__init__` (previously the attribute did not exist until the first `iTC_goto_targetT()` call, hence the scattered `hasattr()` guards, all now replaced with `is not None` checks). `iTC_goto_targetT()` returns a bool indicating whether a thread was really started, and the temperature loop only builds the `QEventLoop` and waits when that is true. Previously, with `ScanT` ticked but the iTC disconnected, the caller still touched `self.itc_stab_thread`, raising `AttributeError` on the first run or blocking the scan thread forever on a stale thread whose `finished` signal had already fired.
  - **Converted `MercuryiTC_Updater` from a `QTimer` helper class into a `QThread`.** It previously ran the blocking VISA reads directly on the GUI thread on every timer tick, stalling the UI while real-time temperature display was enabled. Polling now happens in `run()`, and readings reach the UI through a `display_updated` signal handled by an `@Slot(dict) update_ui_display()`. The old `iTC_timer` / `update_disp_oneshot()` members were removed with no orphaned references left. `closeInstruments()` now also stops and waits for this thread before closing the MercuryiTC handle, so it cannot keep polling a closed instrument.
  - **Added a pre-scan instrument check.** New `check_instruments_ready()` returns the display names of devices ticked "active" but not connected (and flags the case where nothing is active at all). `runScan()` refuses to start, prints the list and shows a `QMessageBox` warning, instead of running the whole loop against `None` devices and writing a file full of zeros.
  - **Guarded the single-point FFT crash.** `update_TDS_FDS_chart()` only checked for *empty* data, so a one-point trace passed the guard, plotted, then crashed in `thz_fft_calc()` with `ValueError: zero-size array to reduction operation minimum` (`np.diff` of a 1-element array is empty). Added a `len(x) < 2` guard: the TDS curve is still drawn, the FDS/FFT update is skipped, and a warning naming the likely step-size/step-NO misconfiguration is printed.
  - **Wait-time multipliers now accept decimals.** `wait1multip` and `wait2multip` were changed from `QSpinBox` to `QDoubleSpinBox` (2 decimals, range 0.1-10.0, step 0.1, default 2.0), and `apply_lockin_parameter()` now does `int(round(timeConst_ms * multiplier))` so the float result is rounded rather than truncated.
  - **Deliberately not changed:** the `TPOP_Data` save directory (correct for this system, per user), and all peak-tracking work from OPTP. The single `processEvents()` inside `update_iPos2_from_tds_peak()` was also left in place - it belongs to MO's own pre-existing peak-tracking path and fires at most once per sweep, so it is not a flood source.
- Verification: `python -m py_compile` passes. The `.ui` was re-loaded through `QUiLoader` (offscreen) to confirm it still renders and that both multiplier boxes are now `QDoubleSpinBox` accepting 1.2 and reading it back exactly. A source-level audit then confirmed each fix landed: 0 `processEvents()` left in the high-frequency slots, 0 `itc_stab_thread.quit()` calls, 0 legacy `hasattr()` guards, `itc_stab_thread` initialised to `None`, `iTC_goto_targetT()` declared `-> bool`, the `stab_started` guard present in the temperature loop, `MercuryiTC_Updater` deriving from `QThread` with `run()`/`update_ui_display()` and 0 `iTC_timer` references, and the `check_instruments_ready()`, `len(x) < 2` and `int(round(...))` changes all present. Not yet exercised against real hardware - in particular the chart refresh rate after removing `processEvents()`, and the real-time temperature display now that it polls off-thread, both need a live run.

### v2.1 (abort scan on failed temperature stabilization)
- Date: 2026-08-10
- Main change: Ported the OPTP v2.5 fix so the scan no longer continues after temperature stabilization has failed, and corrected the placement of the sample-soak wait.
- Details:
  - Problem (same as OPTP): `iTCstabilizeThread.finished` is a `Signal(bool)` emitted with `False` on failure paths (iTC not connected, an exception inside the poll loop such as a failed `read_temperature()`, and a user stop) and `True` only on a genuine settle. The temperature loop connected it as `finished.connect(loop_for_Tstab.quit)`, and `quit()` takes no arguments, so the bool was silently discarded: the wait ended immediately, the temperature-done LED went green unconditionally, and the scan proceeded at an uncontrolled temperature under a `..._{target_T}K` file name.
  - Fix: `iTCstabilizeThread` now records its outcome as plain state (`self.stab_success`, reset at the top of `run()`, set True only immediately before `finished.emit(True)`). The temperature loop reads it after the wait, emits `temp_done_led` with the real result instead of a hardcoded `True`, and `break`s out of the temperature loop with an explicit message when stabilization failed.
  - State is used rather than the signal payload deliberately: the caller connects to `finished` only after `iTC_goto_targetT()` has already started the thread, so a thread that fails immediately can emit `finished` before the connection exists - the payload would never arrive and `loop_for_Tstab.exec()` would block forever. The event loop is now entered only `if self.itc_stab_thread.isRunning()`, closing that deadlock.
  - Also fixed a placement bug introduced when the soak wait was first added to this file: `wait_sample_stable()` sat outside the `if stab_started ...` / `else` pair, so with the iTC disconnected the else-branch still fell through into the wait and burned the full soak time (10 min by default) for a temperature point that was never stabilized at all. It now lives inside the success branch, matching OPTP.
  - Not changed: no temperature re-check after the soak. The MercuryiTC regulates in hardware (`enable_auto_pid_table` / `enable_pid_control` are one-shot writes; the stabilization thread only observes), and `MercuryiTC_Updater` - now a `QThread` - keeps polling with `realtimeDispT` whitelisted during scans, so the temperature stays controlled and visibly displayed throughout the soak.
- Verification: `python -m py_compile` passes. All `run()` exit paths were simulated against the caller's decision logic: only a genuine settle proceeds to the soak and the scan; iTC-not-connected, a read exception and a user stop all abort.

- Date: 2026-08-15
- Main change: Initialized v2.2 version copies (`MO_system_iTC_v2.2.py` and `MO_system_iTC_v2.2.ui`) from v2.1, and ported the two `closeInstruments()` fixes from OPTP v2.6/v2.7. Checked first that this system holds no hidden dependency on the shared-library change made alongside them.
- Details:
  - Duplicated main executable script and Qt UI layout file for v2.2 development; linked `MO_system_iTC_v2.2.py` to load `MO_system_iTC_v2.2.ui`.
  - **Shared-library impact check.** The fix applied in `inst_libs/` (removing `self._rm.close()`, since `pyvisa.ResourceManager()` is a process-wide singleton and closing it invalidated every other instrument's session) affects this system too. Grepped `MO_system_iTC_v2.1.py` and `OPTP_image_System/OPTP_iTC_image_v1.0.py` for `ResourceManager` / `_rm`: no application-level references at all, so neither relies on the old teardown behaviour and both simply benefit from the fix. Originals are backed up in `inst_libs/backup_before_rm_fix/`.
  - **Selective close (ported from OPTP v2.6).** Every block in `closeInstruments()` tested only `if self.<device>:` and never the matching `active*` checkbox, so unticking a box and pressing "Close Instr." still dropped every connected instrument. Added a `should_close()` helper gating each device on its checkbox, mirroring `connectInstruments()`.
  - `closeInstruments()` gained `only_active: bool = True`; `exitApp()` now calls it with `only_active=False` so anything still open is released on exit even if its box was unticked, rather than leaving the port locked.
  - The button connection was rewritten as `clicked.connect(lambda: self.closeInstruments(only_active=True), False)`. Required, not cosmetic: `clicked` emits a `checked` bool which Qt otherwise passes into the slot's first parameter, forcing `only_active=False` and silently defeating the fix (verified empirically in the OPTP work).
  - **Failure isolation (ported from OPTP v2.7).** Each instrument now closes through a `close_one()` helper: a raising `close()` is logged as a warning and the sequence continues, with the reference and LED cleared in a `finally` block since the session is gone either way. The MercuryiTC block got the same treatment plus a message pointing at remote mode. Previously one dead session aborted the whole shutdown and left every remaining instrument open with its port locked - the failure mode reported on OPTP, where taking the iTC controller out of remote/unlock mode raised `VI_ERROR_INV_OBJECT`.
  - The `iTCstabilizeThread` and `MercuryiTC_Updater` shutdowns were moved inside the `closing_itc` branch. `request_stop()` also raises the main `stop_flag`, which aborts a running scan; that must not happen just because an unrelated instrument is being closed.
- Verification: `python -m py_compile` passes. The real `closeInstruments()` was extracted and run against stubs in three scenarios: with only Stage1 and Lock-in 1 ticked exactly those two closed, the other six stayed connected and the stabilization thread was *not* stopped (so a running scan would survive); with `only_active=False` all eight were released and the iTC threads were stopped; and with the MercuryiTC rigged to raise `VI_ERROR_INV_OBJECT` the call did not propagate, the other seven still closed, every reference was cleared and the failure was reported as a warning. Not yet exercised against real hardware.

### v2.2 (rotary connection failure handling)
- Date: 2026-09-15
- Main change: Rotary1/2/3 now follow the same "temp object, release and reset to `None` on failure" connection pattern already used by the linear stages, so a half-initialised rotary can no longer be mistaken for a connected one.
- Details:
  - Found while fixing the same defect in `THz_emission_system/THz_emission_system_iTC_v1.1.py`; this system carries an identical copy of the three rotary blocks.
  - Before: each block did `self.rotaryX = RotaryStage(...)` first and called `home(60000)` afterwards inside the same `try`. If the controller connected but homing failed, the exception was caught and only printed, leaving `self.rotaryX` holding a live but un-referenced object.
  - Consequence: `check_instruments_ready()` saw a non-`None` attribute and reported the rotary as ready and `move_active_stages()` then issued `move_to()` commands to a stage that had never been homed, so every recorded position for that axis was meaningless. The USB handle was also never released, keeping the port locked until the application exited.
  - After: each block builds `rotaryX_temp`, homes it, and assigns `self.rotaryX = rotaryX_temp` only once both steps succeeded. The `except` branch closes the temp object (errors during close are swallowed), sets `self.rotaryX = None`, and prints the same failure message as before.
  - Only the three connection blocks were touched: serials, channels, homing timeout, poll interval, `qwait_time()` calls, LED updates and all print messages are unchanged.
  - This system's rotary blocks have a slightly different layout (a `qwait_time(300)` between construction and homing, and another one after it); the surrounding waits were preserved exactly, only the assignment target moved.
  - Stage1 in this file already used the guarded pattern, so it needed no change.
  - Known issue found but NOT fixed here: the Stage2 (PM500) block has a worse variant of the same defect. `self.stage2 = PM500(RESOURCE)` is assigned *outside* the `try`, then reassigned by `PM500(RESOURCE).connect()` inside it, so a failure anywhere in the block leaves `self.stage2` pointing at a live, unconnected object - and the first assignment's handle is dropped without being closed. It also catches only `PM500Error`, so a VISA-level failure escapes `connectInstruments()` entirely and skips every instrument after it. Left alone because this round was scoped to the rotary stages.
- Verification: `python -m ast` parses the patched file. The patch was applied by a line-based script that locates each `try` / `except Exception as e:` pair by its `✗ RotaryN connection failed` message and rewrites only the lines inside; running the same script against the already-fixed THz v1.2 file correctly reported "already patched" for all three blocks, confirming it does not double-apply. The failure branch itself is not runtime-tested because it needs the real controllers.
