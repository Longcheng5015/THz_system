# OPTP Image System Development Change Log

This document records the overall development and debugging history for the OPTP_image_System project, including version updates, bug fixes, and major functional changes.

## Version history


### v1.1
- Date: 2026-08-15
- Main change: Initialized v1.1 version copies (`OPTP_iTC_image_v1.1.py` and `OPTP_iTC_image_v1.1.ui`) from v1.0, and ported the two `closeInstruments()` fixes from OPTP v2.6/v2.7 (also applied to MO v2.2). This system had both defects.
- Details:
  - Duplicated main executable script and Qt UI layout file for v1.1 development; linked `OPTP_iTC_image_v1.1.py` to load `OPTP_iTC_image_v1.1.ui`.
  - **Shared-library context.** `inst_libs/` was fixed separately by removing `self._rm.close()` from the instrument `close()` methods: `pyvisa.ResourceManager()` is a process-wide singleton (verified - constructing it twice returns the same object, pyvisa 1.16.2), so every instrument held the same manager and closing it invalidated all the other sessions. That produced `VI_ERROR_INV_OBJECT` during shutdown once any one session had already died. This system was grepped for `ResourceManager` / `_rm` and has no application-level references, so it holds no dependency on the old behaviour and simply benefits. Originals are backed up in `inst_libs/backup_before_rm_fix/`.
  - **Selective close.** Every block in `closeInstruments()` tested only `if self.<device>:` and never the matching `active*` checkbox, unlike `connectInstruments()`. Unticking a box and pressing "Close Instr." therefore still dropped every connected instrument. Added a `should_close()` helper gating each device on its checkbox.
  - `closeInstruments()` gained `only_active: bool = True`; `exitApp()` now calls it with `only_active=False` so anything still open is released on exit even if its box was unticked, rather than leaving the port locked.
  - The button connection was rewritten as `clicked.connect(lambda: self.closeInstruments(only_active=True), False)`. Required, not cosmetic: `clicked` emits a `checked` bool which Qt otherwise passes into the slot's first parameter, forcing `only_active=False` and silently defeating the fix.
  - **Failure isolation.** Each instrument now closes through a `close_one()` helper: a raising `close()` is logged as a warning and the sequence continues, with the reference and LED cleared in a `finally` block since the session is gone either way. The MercuryiTC block got the same treatment plus a message pointing at remote mode. Previously one dead session aborted the whole shutdown and left every remaining instrument open with its port locked.
- Verification: `python -m py_compile` passes. The real `closeInstruments()` was extracted and run against stubs in three scenarios: with only Stage1 and Lock-in 1 ticked exactly those two closed and the other six stayed connected; with `only_active=False` all eight were released; and with the MercuryiTC rigged to raise `VI_ERROR_INV_OBJECT` the call did not propagate, the other seven still closed and every reference was cleared. Not yet exercised against real hardware.
- Known issues left untouched in this version (present in v1.0, not part of this fix): `closeInstruments()` does not stop the `iTCstabilizeThread` or the display updater before closing the MercuryiTC, `self.itc_stab_thread` is never initialised to `None` in `__init__`, `MercuryiTC_Updater` is still a plain `QTimer`-driven class doing blocking VISA reads on the GUI thread, and `uid_HTR` / `uid_TEMP` are not cleared when the iTC is closed. The equivalent fixes exist in OPTP v2.4+ and MO v2.1+ if they are wanted here later.

### v1.2
- Date: 2026-08-15
- Main change: Initialized v1.2 version copies (`OPTP_iTC_image_v1.2.py` and `OPTP_iTC_image_v1.2.ui`) from v1.1, and back-ported the remaining stability fixes accumulated in OPTP v1.9 - v2.5. Peak tracking was deliberately left untouched, as requested.
- Details:
  - **Removed `QApplication.processEvents()` from the 8 high-frequency scan slots** (`update_curr_repeat`, `update_curr_pos`, `update_curr_step`, `update_curr_stepNOs`, `update_lockin_charts`, `update_pol_chart` x2, `update_TDS_FDS_chart`). Those slots already run on the GUI thread via queued connections, so `processEvents()` re-entered the event loop and dispatched the next queued scan signal from inside the current slot. When the scan loop emits faster than the GUI drains - most easily with instruments missing, where there is no hardware latency - the nesting grew without bound until the stack overflowed and the process was killed with no Python traceback. Kept the calls in `connectInstruments()`, `closeInstruments()`, `iTC_goto_targetT()` (button path) and `set_ControlsEnabledDuringScan()`, which are main-thread user actions.
  - **Fixed the stabilization-thread lifetime.** `iTC_goto_targetT()` previously overwrote `self.itc_stab_thread` with no cleanup at all, which triggers "QThread: Destroyed while thread is still running". It now sets the stale thread's own `stop_flag` (not `self.stop_flag`, which would also abort a running scan) and waits with a 2 s timeout before creating the replacement. Note this system never had the intermediate `quit()` + unbounded `wait()` form seen in MO - it simply had no cleanup, which is worse.
  - **Hardened `itc_stab_thread` state.** Initialised to `None` in `__init__` (the attribute previously did not exist until first use, hence the `hasattr()` guards, all now replaced with `is not None`). `iTC_goto_targetT()` returns a bool indicating whether a thread was really started, and the temperature loop only builds the `QEventLoop` and waits when that is true - otherwise a disconnected iTC caused either `AttributeError` or a permanent block on a stale thread whose `finished` signal had already fired.
  - **Abort the scan when stabilization fails.** `iTCstabilizeThread.finished` is a `Signal(bool)` emitted `False` on four failure paths (iTC not connected, missing UID, an exception in the poll loop, a user stop) and `True` only on a genuine settle, but the loop connected it as `finished.connect(loop_for_Tstab.quit)` and `quit()` takes no arguments, so the bool was discarded and the scan continued at an uncontrolled temperature under a `..._{target_T}K` file name. The thread now also records `stab_success` as plain state; the loop reads that, emits `temp_done_led` with the real result instead of a hardcoded `True`, and breaks out of the temperature loop on failure. State is used rather than the signal payload because the caller connects only after the thread is started, so an immediate failure would emit before the connection exists - the event loop is now entered only `if isRunning()`, closing that deadlock too.
  - **Converted `MercuryiTC_Updater` from a `QTimer` helper class into a `QThread`.** It previously ran blocking VISA reads directly on the GUI thread on every tick, stalling the UI while real-time temperature display was enabled. Polling now happens in `run()` and readings reach the UI through a `display_updated` signal handled by an `@Slot(dict) update_ui_display()`. The old `iTC_timer` / `update_disp_oneshot()` members were removed with no orphaned references left, and `closeInstruments()` now stops both the updater and the stabilization thread before closing the MercuryiTC handle so neither can poll a closed instrument.
  - **Added a pre-scan instrument check.** New `check_instruments_ready()` returns the display names of devices ticked "active" but not connected (and flags the case where nothing is active at all). `runScan()` refuses to start, prints the list and shows a `QMessageBox` warning, instead of running the whole loop against `None` devices and writing a file full of zeros.
  - **Guarded the single-point FFT crash.** `update_TDS_FDS_chart()` only checked for *empty* data, so a one-point trace passed the guard, plotted, then crashed in `thz_fft_calc()` with `ValueError: zero-size array to reduction operation minimum`. Added a `len(x) < 2` guard: the TDS curve is still drawn and the FDS/FFT update is skipped with a warning.
  - **Wait-time multipliers now accept decimals.** `wait1multip` and `wait2multip` changed from `QSpinBox` to `QDoubleSpinBox` (2 decimals, range 0.1-10.0, step 0.1, default 2.0), and `apply_lockin_parameter()` now does `int(round(timeConst_ms * multiplier))` so the float result is rounded rather than truncated.
  - `uid_HTR` / `uid_TEMP` are now cleared when the MercuryiTC is closed; previously they kept stale values.
  - **Not changed:** the peak-tracking code (`get_TDS_peak_pos` and its call site) is untouched. The `ext_info` filename suffix and the `WaitSamStable` sample-soak wait were also left out - those are new features needing new UI widgets, not defects in this system.
- Verification: `python -m py_compile` passes and the modified `.ui` loads through `QUiLoader` (offscreen) with both multiplier boxes resolving as `QDoubleSpinBox` accepting 1.2 and reading it back exactly. A 15-point source audit confirmed every fix landed (0 `processEvents()` in scan slots, 0 `iTC_timer` references, 0 legacy `hasattr()` guards, and each new symbol present). `check_instruments_ready()` and `closeInstruments()` were then extracted and executed against stubs: the readiness check correctly lists ticked-but-unconnected devices, passes a connected setup and flags an all-unticked one; the close path closes only ticked instruments without stopping the stabilization thread, releases all eight on the exit path, and survives a MercuryiTC raising `VI_ERROR_INV_OBJECT` with the other seven still closed and the uid state cleared. Not yet exercised against real hardware.

### v1.2 (rotary connection failure handling)
- Date: 2026-09-15
- Main change: Rotary1/2/3 now follow the same "temp object, release and reset to `None` on failure" connection pattern already used by the linear stages, so a half-initialised rotary can no longer be mistaken for a connected one.
- Details:
  - Found while fixing the same defect in `THz_emission_system/THz_emission_system_iTC_v1.1.py`; this system carries an identical copy of the three rotary blocks.
  - Before: each block did `self.rotaryX = RotaryStage(...)` first and called `home(60000)` afterwards inside the same `try`. If the controller connected but homing failed, the exception was caught and only printed, leaving `self.rotaryX` holding a live but un-referenced object.
  - Consequence: `check_instruments_ready()` saw a non-`None` attribute and reported the rotary as ready and `move_active_stages()` then issued `move_to()` commands to a stage that had never been homed, so every recorded position for that axis was meaningless. The USB handle was also never released, keeping the port locked until the application exited.
  - After: each block builds `rotaryX_temp`, homes it, and assigns `self.rotaryX = rotaryX_temp` only once both steps succeeded. The `except` branch closes the temp object (errors during close are swallowed), sets `self.rotaryX = None`, and prints the same failure message as before.
  - Only the three connection blocks were touched: serials, channels, homing timeout, poll interval, `qwait_time()` calls, LED updates and all print messages are unchanged.
  - Known issue found but NOT fixed here: `Stage1` and `Stage2` in this file have exactly the same defect (`self.stageX = LinearStage(...)` followed by `self.stageX.home(60000)` in one `try`, with the `except` only printing). They were left alone because this round was scoped to the rotary stages; OPTP v2.8 and MO v2.2 already carry the guarded pattern for their linear stages, so this system is the only one still exposed.
- Verification: `python -m ast` parses the patched file. The patch was applied by a line-based script that locates each `try` / `except Exception as e:` pair by its `✗ RotaryN connection failed` message and rewrites only the lines inside; running the same script against the already-fixed THz v1.2 file correctly reported "already patched" for all three blocks, confirming it does not double-apply. The failure branch itself is not runtime-tested because it needs the real controllers.

### v1.2 (2D_THz scan order: stage1 made the innermost axis)
- Date: 2026-09-15
- Main change: in `2D_THz`, one full stage1 time-domain trace is now recorded at each stage2 pump delay, instead of sweeping stage2 at each stage1 point.
- Details:
  - the shared `ScanPlanner.build_scan_iterator()` yields `itertools.product(pol, stage1, stage2)` for every non-POL_2D mode, and `product` varies its last argument fastest, so stage2 was the innermost axis. The nesting was polarization (slowest) -> stage1 -> stage2 (fastest), i.e. a full pump-delay sweep at each THz delay point - the opposite of what the mode means and of what the scanMode tooltip says,
  - two consequences of the old order: a single time-domain trace took as long as the whole 2D scan to accumulate, so slow laser drift appeared as waveform distortion rather than point-to-point noise; and the live TDS chart, gated on `stage1_idx == stage1_NO - 1`, only fired at the very end of each polarization block and then emitted `stage2_NO` times in a row,
  - `func_cores/scan_func_core.py` is shared by this system, OPTP, OPTP image and MO, so it was deliberately left untouched. The reordering is done in `OPTP_iTC_image_v1.2.py` only: right after `build_scan_iterator()` returns, a `2D_THz` run replaces `scan_iterator` with a locally built generator nested `pol -> stage2 -> stage1`, using the totals the planner already returns through the `stage1_total` / `stage2_total` / `pol_total` locals this file already extracts,
  - the tuple layout is unchanged - `(stage1_flat_idx, stage2_flat_idx, pol_flat_idx)` - so `decode_scan_indices()`, the HDF5 index tuple and every display slot are untouched. Only `2D_THz` is affected; `THz_Scan`, `1D_Scan`, `POL_1D` and `2D_IMG` still use the planner's iterator verbatim,
  - confirmed this system needs the change: its `2D_THz` TDS chart is fed with `stage1_pos_sequence`, so stage1 is the THz delay line here. MO v2.2 was deliberately left alone - there `2D_THz` feeds the chart with `stage2_pos_sequence`, so stage2 is its delay line and the existing stage2-innermost order is already correct,
  - verified by driving the real planner plus the same override with 3 stage1 points x 2 stage2 points x 2 polarization states: the order is stage1 0,1,2 at stage2=0, then stage1 0,1,2 at stage2=1, then the same for the second polarization state, and the TDS chart condition fires exactly 4 times (once per pump delay per polarization state) instead of bursting at the end. The chart's data slice `ds_lockin1_X[:, rep, stage2_idx, ...]` is complete at every emit. Not yet exercised against real hardware.
